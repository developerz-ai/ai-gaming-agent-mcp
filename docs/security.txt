AI GAMING AGENT - Security Guide
==================================

SECURITY LAYERS
---------------
The system implements multiple security measures:

  1. Password/Token Authentication
     - Required for all connections
     - Validated on every request
     - Checked first: an invalid token is refused with 401 before any
       Host or Origin check runs
     - An empty configured password refuses every request with 403

  2. DNS-Rebinding Protection (transport layer)
     - The Host and Origin headers of every /mcp request are validated
       against the configured allow-lists
     - Allowed hosts: server.allowed_hosts
       (default: localhost:*, 127.0.0.1:*, [::1]:* - loopback only)
     - Allowed origins: server.allowed_origins
       (default: http://localhost:*, http://127.0.0.1:*, http://[::1]:* -
       loopback only)
     - A Host outside the allow-list is refused with 421
       ("Invalid Host header") and never reaches the SSE transport
     - An Origin outside the allow-list is refused with 403
       ("Invalid Origin header") and never reaches the SSE transport
     - An entry matches exactly, or any host:port form of that host when it
       ends in ":*"
     - The wildcard covers host:port forms only: "192.168.1.100:*" matches
       "192.168.1.100:8765" but not the bare "192.168.1.100" or
       "http://192.168.1.100", which need their own exact entries (otherwise
       they are refused with 421/403)
     - A remote PC must list its own address (e.g. 192.168.1.100:8765) or
       every /mcp request from that client is refused with 421
     - Environment overrides: GAMING_AGENT_SERVER__ALLOWED_HOSTS and
       GAMING_AGENT_SERVER__ALLOWED_ORIGINS (JSON array values). A config
       file's values win over them
     - GET /health is neither authenticated nor Host-validated

  3. Path Restrictions
     - File access limited to allowed directories
     - Prevents access to system files
     - An empty security.allowed_paths means no restriction at all: set it
       to the game directories to restrict access

  4. Command Blocklist
     - Dangerous commands are blocked
     - Prevents system damage

  5. TLS/HTTPS (terminated by a reverse proxy)
     - The server itself speaks plain HTTP and does not terminate TLS
     - Encryption is the reverse proxy's job (nginx, Caddy, ...)
     - Recommended for production


NOT IMPLEMENTED
---------------
The following are NOT protections in this release:

  - Rate Limiting - NOT IMPLEMENTED (planned only)
    - Rate limiting is not currently implemented: there is no per-minute
      request cap, no per-IP throttle and no lockout, so failed
      authentications are unlimited
    - The bearer token is therefore NOT brute-force mitigation
    - Because it is not implemented, rate limiting has to come from an
      external limiter (reverse proxy or firewall) or from keeping the
      server on a private network

  - Audit Trail - NOT IMPLEMENTED (planned only)
    - The server writes no audit trail and no ~/.gaming-agent/logs/*.log
      files
    - It emits Python logging records on stdout/stderr instead (see
      LOGGING AND MONITORING)


AUTHENTICATION FLOW
-------------------
  1. Client sends HTTP request with Authorization header
  2. Header format: "Bearer <password>"
  3. Server validates password against config
  4. If invalid: return 401 Unauthorized
  5. If valid: validate Host and Origin against the allow-lists
     - Host not allowed: return 421 ("Invalid Host header")
     - Origin present and not allowed: return 403 ("Invalid Origin header")
  6. If valid: establish SSE connection


BEST PRACTICES - DO
-------------------
  - Use strong, unique passwords (16+ characters)
  - Use different passwords for each PC
  - List every remote PC explicitly in server.allowed_hosts
  - Limit file access to game directories only
  - Use VPN when accessing over internet
  - Terminate TLS/HTTPS at a reverse proxy for production
  - Put an external rate limiter (reverse proxy, firewall) in front of the
    server - the server has none of its own
  - Rotate passwords regularly
  - Capture the server's stdout/stderr output and review it periodically
    (there is no audit log)
  - Keep software updated


BEST PRACTICES - DON'T
----------------------
  - Expose port directly to internet without VPN
  - Use simple or default passwords
  - Allow unrestricted command execution
  - Give access to system directories
  - Run server as root/admin unless required
  - Share passwords across multiple systems
  - Ignore authentication failures in the server output
  - Widen server.allowed_hosts / server.allowed_origins to a wildcard


NETWORK SECURITY
----------------

Local Network Only (Recommended for beginners):
  - Bind to local IP only
  - Use network firewall
  - No internet exposure

VPN Access (Recommended for remote):
  - Use WireGuard, OpenVPN, or Tailscale
  - Gaming PCs only accessible via VPN
  - Full encryption of traffic
  - Add the VPN address of each PC to server.allowed_hosts

Direct Internet (Not Recommended):
  - Requires TLS/HTTPS
  - Strong password essential
  - No built-in rate limiting: put an external limiter or IP allowlist in
    front of the server
  - Consider IP allowlisting
  - Monitor for attacks


COMMAND EXECUTION SAFETY
------------------------
The execute_command tool is powerful but dangerous.

Recommended blocked commands:
  - rm -rf, del /f (destructive deletion)
  - format (disk formatting)
  - shutdown, reboot (system control)
  - chmod 777, icacls (permission changes)
  - curl | bash (remote code execution)

Set reasonable timeout limits (30 seconds default).


FILE ACCESS SAFETY
------------------
Limit allowed_paths to:
  - Game installation directory
  - Game save/data directory
  - Temporary screenshot folder

Never allow:
  - System directories (Windows, System32, /etc)
  - User profile root
  - Password/credential storage locations


LOGGING AND MONITORING
----------------------
The server writes no log or audit files of its own. It emits Python logging
records on stdout/stderr:

  - A wrong token and a missing configured password are logged as warnings
  - Nothing in the package configures a logging handler, and the root logger
    stays at WARNING, so the info-level records the server writes (server
    start/stop, each new SSE connection) are dropped before any handler sees
    them: no start/stop or connection record reaches the output
  - Warning-and-above records do reach stderr: the failed authentications
    above, plus the workflow engine's warnings and exceptions (a screenshot
    that failed, a terminal that would not close)
  - Uvicorn's access and error output is mixed into the same stdout/stderr
    streams

Tool executions are not logged: the output shows no record of the commands
run or the files read. Use host-level auditing if you need that trail.

Capture the output if you want a record:

  gaming-agent serve 2>&1 | tee -a server.log

Review the captured output regularly for:
  - Failed authentication attempts
  - Unexpected connections


INCIDENT RESPONSE
-----------------
If you suspect unauthorized access:

  1. Stop the MCP server immediately
  2. Change passwords
  3. Review the captured server output for failed authentication attempts
  4. Check for unauthorized file changes
  5. Restart with new configuration
  6. Consider additional security measures
